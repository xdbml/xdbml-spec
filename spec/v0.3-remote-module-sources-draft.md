# Module System: Remote Sources (xDBML v0.3 draft)

> Editorial note. The subsection numbers below are provisional. The feature is a single new subsection of §25 (Module System), "Remote module sources," with nested sub-subsections; it therefore consumes one top-level §25 number, and the renumbered §10 to §30 are unaffected. Reconcile the local numbers against the live §25 outline on integration. The directive examples follow the v0.2 grammar's `useDirective` rule, `(use | reuse) (* | { elementType name [as alias], ... }) from STRING_LITERAL`, verified against `grammar/xDBML.g4` on `main`. A URL is an ordinary single-quoted `STRING_LITERAL`, so this revision requires no grammar change; scheme detection and the rejection rules are semantic-pass concerns, consistent with the grammar's permissive-parse design.

## 25.x Remote module sources

Through v0.2, an import source was always a relative path to another xDBML file. This revision adds a second form of source: an absolute URL retrieved over HTTPS. A remote source is recognized purely by its scheme. A source string that begins with `https://` is a remote source; any other source string is a relative path and is resolved exactly as in v0.2.

Only the `https` scheme is permitted. A source that uses `http`, `file`, `git`, `ssh`, `data`, a protocol-relative form such as `//host/path`, or a bare host such as `github.com/owner/repo/...` MUST be rejected with a located error. It is never reinterpreted as a relative path. Plaintext transport is not acceptable for content that the importing document will trust as schema, and the other forms are excluded so that the boundary between local and remote resolution stays unambiguous.

A remote source changes only where the bytes of a module come from. It does not change what an import does. The directive-location-equals-placement-location principle of §25 is preserved without modification: an import placed at a given directive location places the imported objects at that location, whether the source is a path or a URL. The field-import exception is likewise unchanged. Both directive keywords (`use` and `reuse`), both selection forms (the import-all `*` and the selective `{ ... }` list), per-symbol `as` aliasing, and any directive settings behave identically whether the string after `from` is a path or a URL, and they bind imported objects the same way.

```
// Import everything a remote module exposes
use * from 'https://raw.githubusercontent.com/acme/schemas/v1.4.0/core.xdbml'

// Import selected objects; each item carries its element-type slot,
// and an optional per-symbol alias
reuse { entity Customer, entity Order as SalesOrder } from 'https://raw.githubusercontent.com/acme/schemas/v1.4.0/sales.xdbml'

// A relative source continues to work exactly as before
use * from './local/inventory.xdbml'
```

### 25.x.1 Resolving relative references inside a remote module

A remote module may itself contain imports. When a remote module contains a relative source, that source is resolved against the base URL of the module that contains it, following the reference resolution rules of RFC 3986. It is not resolved against the entry document, and it is not resolved against any filesystem location.

For example, if a local entry document imports `https://raw.githubusercontent.com/acme/schemas/v1.4.0/core.xdbml`, and `core.xdbml` contains the relative source `./enums.xdbml`, that reference resolves to `https://raw.githubusercontent.com/acme/schemas/v1.4.0/enums.xdbml`. This lets an author publish a multi-file module set, expose a single entry file, and rely on the set's internal references continuing to work once the entry file is imported by URL.

A consequence of resolving against the containing module's base URL is that a remote module can never reach the local filesystem. Every reference resolved against an `https` base is itself an `https` URL. This is a deliberate trust boundary: importing a remote module grants that module no access to the importing system's files.

### 25.x.2 Pinning and reproducibility

A URL that names a mutable reference, such as a branch, can return different content over time, so the same import may yield a different model on a later resolution. To keep a model reproducible, an author SHOULD pin a remote source to an immutable reference, such as a commit identifier or a release tag, rather than a branch name.

The following table shows immutable raw-content URL forms for common hosts. These forms are informative guidance, not part of the language.

| Host | Immutable raw-content form (informative) |
|---|---|
| GitHub | `https://raw.githubusercontent.com/{owner}/{repo}/{commit-or-tag}/{path}` |
| GitLab | `https://gitlab.com/{owner}/{repo}/-/raw/{commit-or-tag}/{path}` |
| Bitbucket Cloud | `https://bitbucket.org/{workspace}/{repo}/raw/{commit-or-tag}/{path}` |
| Azure DevOps | `https://dev.azure.com/{org}/{project}/_apis/git/repositories/{repo}/items?path=/{path}&versionDescriptor.version={commit}&versionDescriptor.versionType=commit&download=true&api-version=7.1` |

Note: each host also serves a human-facing page, a "blob," "src," or "browse" view, at a different URL that returns HTML rather than raw content. A remote source MUST point at the raw-content URL. Recognizing and rewriting a human-facing URL into a raw-content URL is out of scope for the language and is addressed under resolver conformance. Azure DevOps in particular has no dedicated raw host and serves content through its Items API, which typically also requires authentication; see §25.x.4.

### 25.x.3 Resolution failures

Remote resolution can fail in ways local resolution cannot. A resolver MUST treat every one of the following as a hard error that aborts resolution with a located diagnostic. It MUST NOT drop the failed import silently, and it MUST NOT substitute a partial model for the missing one.

The conditions are: a network or DNS failure; a response status outside the 2xx range; a request that exceeds the resolver's timeout; a TLS failure; a redirect to a non-`https` target; a redirect chain longer than the resolver's limit; a response larger than the resolver's size limit; and content that does not parse as a valid xDBML module. This requirement exists because a silent file-level drop produces a model that looks complete but is not, which is a known and costly failure mode of module resolution.

### 25.x.4 Credentials and authentication

A remote source MUST NOT carry credentials. Userinfo in the authority component, such as `https://user:token@host/...`, and credential-bearing query parameters, such as an access token appended to the URL, are prohibited, and a resolver MUST reject a source that contains userinfo.

Authentication for private content is outside the scope of the language. A resolver MAY obtain credentials from its own configuration, keyed by host, and apply them when issuing the request. Credentials are never read from, or written to, the document. This keeps private repositories, and hosts that require a token such as Azure DevOps, usable without placing secrets in source that is itself committed to version control.

### 25.x.5 Resolver conformance

The following requirements apply to any resolver that fetches remote sources, and in particular to any resolver that runs in a server context, including a hosted playground or an application backend.

A resolver MUST defend against server-side request forgery. It MUST refuse to resolve sources that target loopback addresses, link-local addresses, private address ranges, or cloud metadata endpoints, unless an operator has explicitly allowlisted them.

A resolver MUST follow redirects only from `https` to `https`, MUST NOT downgrade to a non-`https` target, and MUST bound the number of redirects it follows.

A resolver MUST enforce a maximum response size and a request timeout.

A resolver MAY cache resolved content. When detecting import cycles and de-duplicating fetches, a resolver keys on the normalized URL, with the host lowercased and dot-segments resolved. De-duplication is best-effort, because the same content may be reachable through more than one URL, for example a redirecting host name and its raw-content host name.

Rewriting a human-facing URL into a raw-content URL is permitted as a non-normative convenience, but it is not required and is not part of the language. A resolver that offers this convenience SHOULD document the host patterns it recognizes, and the parser SHOULD NOT be made responsible for host-specific routing, so that the language remains independent of any host's URL conventions.

### 25.x.6 Browser-based resolution and CORS (informative)

A resolver that runs inside a web browser, such as the playground, is subject to the browser's cross-origin policy. A cross-origin fetch succeeds only if the host returns the appropriate cross-origin response headers. In practice, GitHub's raw-content host returns headers that permit cross-origin reads, while the raw or API endpoints of several other hosts do not by default.

The playground therefore attempts to resolve any `https` source and reports a cross-origin failure as a distinct, clearly labeled error rather than a generic fetch failure, so that an author understands the cause. It does not maintain a fixed list of permitted hosts, because cross-origin support can change and can differ on self-hosted instances. An author who needs to resolve sources from a host that does not permit cross-origin reads in the browser should use a server-side resolver. Coverage across all hosts is a property of server-side resolvers, not of browser-based resolution.

### 25.x.7 Future considerations (informative)

Two capabilities are intentionally deferred to a later revision and are noted here so that their absence is understood as deliberate. The first is an integrity attribute on an import, by which an author could record a content hash and a resolver could verify that the fetched content matches it. The second is a guardrail that prevents a relative reference inside a remote module from resolving above a declared base prefix. Neither is part of this revision.
