xDBML -- TablePartial injection applied (after 0.6.5)
Base: origin/main 59ac805 (renderer: automatic arrangement). Built 2026-10-06.
This archive replaces xdbml-tablepartial-injection.zip of earlier today: it
holds that delivery plus `~name` in nested bodies and the 13.5 correction.

The playground showed `users` of spec 17.1 with `name` alone: the three
fields of `base_template` were missing. The parser keeps a `~name` line as
a node of the body, and nothing applied it. The renderer listed the
declared fields only, and so did the other readers of an entity's fields:

  - a Ref to an injected field (`Ref: orders.user_id > users.id`) reported
    "Field 'id' is not declared on entity 'users'", and a top-level
    `records` declaration reported the same for an injected column;
  - an inline `ref:` on a field of a TablePartial drew no relationship;
  - the entity inspector counted 1 field for `users`.

All of these now read the fields through two parser functions,
effectiveFields() and effectiveFieldList(), which apply your decisions:

  1. Injected fields sit where the `~name` line is written, in the order
     the TablePartial declares them. A field the body declares itself
     overrides an injected one and keeps its own place; among partials the
     last one injected applies, at the place of its `~name` line. Checked
     against @dbml/core 10.2.0, which gives the same order in each case.
  2. A TablePartial does not inject another one. `~name` in the body of a
     TablePartial, or inside one of its fields, is the error
     `partial-injection-in-partial`, in every version.
  3. `~name` is allowed among the fields of `object { }` and `json { }`,
     and in the body of a Type or of an entry of `definitions`. The same
     rules of position and conflict apply. Only the fields are placed
     there: a partial's `constraints` block applies at the top level of an
     Entity or an Edge, as before.
  4. `~` names a TablePartial, never a Type. 13.5 is corrected.

HOW TO APPLY
------------
Unzip the archive at the root of the clone (C:\Repos\Hackolade\xdbml-spec),
then, from cmd.exe at the repo root:

    apply.cmd

apply.cmd copies nothing. It checks that 59ac805 is in the history of HEAD
and that no commit since then touched the delivery's files; that each
unzipped file holds this delivery's content; and that the working tree
holds no uncommitted change outside the delivery. It then runs the gate
(npm run check, mcp type-check) and prints the commit commands.

If the earlier archive is already unzipped in the clone and not committed,
unzip this one over it: the file list is the same.

WHAT CHANGED
------------
parser\src\partials.ts (new)
  effectiveFields(decl, partials): the top-level fields of an Entity or an
  Edge with the injected fields in place, each with the TablePartial it
  comes from. effectiveFieldList(items, partials): the same for the fields
  of an object, a json body or a Type. tablePartials(doc),
  injectedPartials(), hasPartialInjection().
parser\src\index.ts
  Exports the five functions and the types EffectiveField, PartialLookup.
parser\src\name-resolver.ts
  Ref endpoints (single, composite, and along a nested path) and top-level
  records columns are looked up among the effective fields. An injected
  field resolves its type names at project scope (15.8.2). New error
  partial-injection-in-partial, at any depth of a TablePartial body.
  unresolved-partial is now also reported in the body of a Type and of an
  entry of definitions, which were not walked.
parser\src\constraints.ts
  The key and index checks and the referenced-key rule (11.17) read the
  effective fields; a key path steps through fields injected in a nested
  object. An inline ref received from a partial is checked for each entity
  that injects it, and a same message is reported once.
parser\src\supertypes.ts
  The redeclaration rule (12.5) reads the effective fields.
renderer\src\layout\layout.ts
  buildEntityLayout(): rows from the effective fields, for entities, Edge
  boxes, and the nested rows of an object, a json body and a Type.
  `unique` lines of an injected partial's constraints block mark their
  rows. With an injection, the PK mark of the top-level rows comes from
  primaryKey(), which applies 10.4. collectRefDeclarations(): the inline
  refs of injected fields, at the top level and in object and json bodies.
playground\src\components\inspector\ast-lookup.ts, Inspector.vue,
FieldInspector.vue, EntityInspector.vue
  A click on an injected row opens the field, at any depth. The
  Identification block names its TablePartial, and Edit in source goes to
  the line in the TablePartial. The field count of the entity includes
  injected fields, and the structural details of a field show its
  `~name` lines.

WHERE THE FIX LANDS
-------------------
The playground on xdbml.org takes it at the site build that follows the
push. The npm packages, the MCP server and the rendering API take it at the
next release. Until then `npm run type-check` in renderer\ fails, since it
compiles against @xdbml/parse 0.6.5 from npm, which lacks the new exports;
that command is not part of the gate, and release.cmd publishes the parser
before it builds the renderer.

OPEN POINTS
-----------
  a. 17.1, 15.6 and 13.5 change the spec text. They sit in the CHANGELOG
     under "Unreleased" without a version mark, and need a number at the
     next point release (0.6.6).
  b. 26 (records) still gives the implicit column order as "locally
     declared fields first, then partial-injected fields in injection
     order", which differs from the order of 17.1. Not changed here.
  c. A partial's settings (headercolor, note) and its `indexes` block are
     not carried to the entity. Upstream DBML carries them, and 17.1 says
     nothing about them.
  d. Two limits met on the way, both older than this delivery and left as
     they were: a Ref path into a `json { }` body reports
     invalid-nested-path whatever the body holds, and an inline `ref:`
     written in the body of a Type draws no relationship for the fields
     typed by it. Fields injected there behave as fields written there.
