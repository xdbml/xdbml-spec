WHAT THIS DELIVERY CHANGES
--------------------------
1. EntityPartial and EntityGroup (spec §17). They are the keywords of
   chapter 17; TablePartial and TableGroup, the DBML keywords, are aliases
   read in every document. A diagram view lists Entities and EntityGroups,
   with Tables and TableGroups as aliases (§18.1); a Metadata block targets
   an EntityGroup (§24.7.1); an import names an entitypartial or an
   entitygroup (§28.3). The AST keeps its node kinds and category names,
   and gains a `keyword` field on partials and groups.

2. color, the header color of an entity (spec §7.5). In a document that
   declares a version, `color` on an entity, a View or an EntityPartial
   sets the header color, as `headercolor` does; written together, they
   are one setting written twice (a warning, the first one applies).
   Without a version declaration, `color` on a Table stays a custom
   property, as DBML 10.3.1 reads it (checked with @dbml/core 10.3.1).

3. Custom properties (spec §24.5, §18.1). A quoted key with the x- prefix,
   "x-hackolade-id", marks a custom property as x_ does. A diagram view
   takes custom properties of any name, as every other element does, in
   its brackets and in Metadata DiagramView blocks: the error
   unknown-diagram-view-setting is gone. The five errors of Studio's
   export, "x-hackolade-id" on diagram views, disappear.

Documents keep declaring `xdbml: 0.7`; the parser also accepts 0.7.1.

The files are in the working tree of your clone, uncommitted, on main.
Look at them with git status and git diff before step 1 if you want.

THE WHOLE DEPLOYMENT, IN THREE COMMANDS
---------------------------------------
From cmd.exe at the repo root (C:\Repos\Hackolade\xdbml-spec), on main:

  apply.cmd            gate, commit this delivery, push main
  apply.cmd release    release 0.7.1, tag v0.7.1
  apply.cmd vscode     publish the VS Code extension 0.7.1

Each step stops at the first failure, says what failed, and can be rerun
once the cause is fixed. Nothing is published before step 2.

Step 1 runs npm run check and the type-check of the MCP server, then
commits every change in the tree as "0.7.1: EntityPartial and EntityGroup,
color as the header color, x- custom properties" and pushes main. It
checks only that the clone is on main and that origin/main has nothing
your main lacks; it does not compare the tree against a list of files.

Step 2 checks that main matches origin/main, runs
tools\release-preflight.cmd 0.7.1, dates the CHANGELOG, and runs
tools\release.cmd 0.7.1: @xdbml/parse and @xdbml/render 0.7.1 on npm, the
MCP server and the rendering API deployed, "release 0.7.1" committed and
pushed, the tag v0.7.1 and its GitHub release from the "## v0.7.1" section
of the CHANGELOG. A point release keeps all three numbers in its tag.

Step 3 publishes tools\vscode-extension\xdbml-0.7.1.vsix, built from the
extension sources of this delivery (vsce package; dist\extension.js is
byte for byte the committed one).
