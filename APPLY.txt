xDBML 0.7.5 -- one rule for the flags of a relationship
Base: main at 67db8da (pull request #8, merged). Built 2026-10-31.

WHAT THIS DELIVERY CHANGES
--------------------------
Pull request #8 made the tools read foreign_master, inactive and
undirected with one rule: the name alone or `: true` sets a flag,
`: false` leaves it unset, and any other value is an error. This release
states the rule in the spec and publishes the tools, so the MCP server
and the rendering API stop drawing `undirected: true` without its
arrows.

The files are in the working tree of your clone, on main, uncommitted:

  spec/v0.7.md         section 11.9 (the three rows, and one sentence
                       under the table), section 11.10 (one word), the
                       description line
  spec/index.md        the v0.7 row names the 0.7.5 point release
  grammar/xDBML.g4     relationshipFlag; undirected alone on an Edge
  grammar/test-cases.md  four v0.7.5 cases
  parser/src/parser.ts   accepts xdbml: 0.7.5
  parser/test/run-tests.ts  the version tests
  CHANGELOG.md         the Unreleased section of #8 becomes v0.7.5
  apply.cmd            the two steps below
  APPLY.txt            this file
  PR-0.7.5.md          the description of the pull request
  COMMIT-0.7.5.txt     the commit message

Step 1 puts the last two in the pull request and the commit and deletes
them, so they are never committed. The VS Code extension, llms.txt and
the MCP reference do not change.

BEFORE YOU START
----------------
Stop wrangler dev, the MCP Inspector and any dev server: Windows locks
their files, and the clean installs of step 2 fail with EPERM. Step 2
needs npm and wrangler logged in; its preflight checks both and says
what to run if either is not.

THE WHOLE DEPLOYMENT, IN TWO COMMANDS
-------------------------------------
From cmd.exe at the repo root (C:\Repos\Hackolade\xdbml-spec), on main:

  apply.cmd            branch, gate, commit this delivery, open the pull request
  apply.cmd release    merge the pull request, release 0.7.5, tag v0.7.5

Each step stops at the first failure, says what failed, and can be rerun
once the cause is fixed. Nothing is published before step 2.

Step 1 checks that the GitHub CLI is logged in and that main is level
with origin/main, then creates the branch dev/0.7.5, which takes the
changes of the working tree. On a rerun it finds itself on dev/0.7.5 and
goes on from there. It runs npm run check and the type-check of the MCP
server, commits every change in the tree except PR-0.7.5.md and
COMMIT-0.7.5.txt, pushes the branch, and opens the pull request into
main.

Step 2 first copies apply.cmd to %TEMP% and runs from the copy. (This is
the fix for the error of the last delivery: switching to main replaced
apply.cmd on disk while it ran, and cmd.exe went on reading the old
script.) It waits for the checks of the pull request, merges it with
--squash --admin, switches to main and pulls. It then runs
tools\release-preflight.cmd 0.7.5, dates the CHANGELOG, and runs
tools\release.cmd 0.7.5:

  - @xdbml/parse and @xdbml/render 0.7.5 published on npm
  - the MCP server and the rendering API deployed with them
  - "release 0.7.5" committed and pushed
  - the tag v0.7.5 and its GitHub release, from the "## v0.7.5" section
    of the CHANGELOG

xdbml.org deploys from main by itself.

IF STEP 2 STOPS
---------------
Before tools\release.cmd starts, rerun apply.cmd release: it finds the
pull request merged and goes on from the pull. Once tools\release.cmd
has started, rerun tools\release.cmd 0.7.5 directly, as the message
says: it skips what it already published, while the preflight refuses a
version that is already on npm.
