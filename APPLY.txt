xDBML -- delta 3 of 4 before 0.5.1: container-qualified Enums
Base: deltas 1 and 2 applied on origin/main 81125b5. Apply them first;
this delta's CHANGELOG.md and run-tests.ts include them.

WHAT CHANGED
------------
Spec §16 already allowed container-qualified Enums, but the parser
rejected the DBML form `enum core.job_status { ... }` ("Expected '{' after
enum name") and a field typed `core.job_status` ("Expected field name").

parser\src\parser.ts
  - parseEnum(): the name may be dotted; each segment may be quoted
    (`enum "billing"."invoice status"`).
  - parseScalarOrNamedType(): a type name may be dotted, with parameters
    after it (`core.money_t(10,2)`). One ScalarType node, name as written.
parser\src\ast.ts
  Doc comments on EnumDeclaration.name and ScalarType.name.
parser\src\name-resolver.ts
  - `enum core.job_status` is filed as enum `job_status` in container
    `core`, the same entry `Container core { Enum job_status }` produces:
    same qualified name, same bare name, and declaring both is
    duplicate-declaration. (Tables are NOT changed: `Table core.users`
    is still filed under the name `core.users`, see chat.)
  - Near miss: a qualified type name compares against qualified names,
    so `core.job_stauts` suggests 'core.job_status'.
  - An unmatched qualified name (`public.geometry`) passes through.
parser\src\module-resolver.ts
  `use { enum core.job_status }` matches the top-level qualified form and
  imports it under its bare name, as it does for a container-scoped Enum
  (the source container does not survive into the importing file, §27.16).
parser\test\run-tests.ts
  6 tests: both declaration spellings, qualified type names with
  parameters and quoted segments, filing and resolution, duplicate across
  the two forms, qualified near miss, cross-file import. All 6 fail against
  the previous sources.
grammar\xDBML.g4
  `scalarType : typeName (...)?` with new `typeName` / `typeNameSegment`
  rules (IDENTIFIER or quotedIdentifier, DOT-separated).
grammar\test-cases.md
  §17.7: one VALID and one INVALID case, both checked against the parser.
spec\v0.5.md -- clarification, no version change (flagged in chat)
  §16: one paragraph and an example: the two ways to declare a
  container-qualified Enum are equivalent, declaring both is a duplicate,
  a field names it by its qualified name. New View in playground button,
  generated with spec-playground-links --write (114 buttons).
CHANGELOG.md
  v0.5 > Changed > Spec: §16 clarification. v0.5 > Fixed > Tooling:
  container-qualified Enums.
