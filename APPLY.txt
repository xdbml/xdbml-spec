Relationship flags read the same way on Refs and Edges -- a tooling fix
Base: main at 6161700 (pull request #7, merged). Built 2026-10-31.

WHAT THIS DELIVERY CHANGES
--------------------------
undirected, inactive and foreign_master now read the same way on every
element that takes them: the name alone, true and 'true' set a flag;
false and 'false' leave it unset; any other value is an error.

  - A Ref accepts undirected written alone, as an Edge did.
  - An Edge reports invalid-undirected for a value such as yes, as a Ref
    did; it accepted any value.
  - undirected: true draws arrows at both ends of a relationship between
    entities. The renderer read the setting as a string only, so
    undirected: 'true' drew them and true did not.
  - inactive: false and foreign_master: false leave the flag unset. They
    set it before, since the tools tested only whether the setting was
    present.
  - inactive and foreign_master with a value other than true or false
    are errors (invalid-inactive, invalid-foreign-master).

There is no version: a tooling change goes out with the next spec
release. Nothing is published to npm, nothing is tagged. The spec,
llms.txt and the MCP reference do not change.

The files are in the working tree of your clone, on main, uncommitted:
the parser (relationships.ts, index.ts, name-resolver.ts) and its tests,
the renderer layout and its tests, the relationship inspector of the
playground, the CHANGELOG (an Unreleased section), and:

  apply.cmd          the two steps below; replaces the one of the
                     Dependabot delivery, whose release step you ran
  APPLY.txt          this file
  PR-flags.md        the description of the pull request
  COMMIT-flags.txt   the commit message

Step 1 puts the last two in the commit and the pull request and deletes
them, so they are never committed.

THE WHOLE DEPLOYMENT, IN TWO COMMANDS
-------------------------------------
From cmd.exe at the repo root (C:\Repos\Hackolade\xdbml-spec), on main:

  apply.cmd            branch, gate, commit this delivery, open the pull request
  apply.cmd release    merge the pull request, bring main up to date

Each step stops at the first failure, says what failed, and can be rerun
once the cause is fixed.

Step 1 checks that the GitHub CLI is logged in and that main is level
with origin/main, then creates the branch fix/relationship-flags, which
takes the changes of the working tree. On a rerun it finds itself on
that branch and goes on from there. It runs npm run check and the
type-check of the MCP server, commits every change in the tree except
PR-flags.md and COMMIT-flags.txt, pushes the branch, and opens the pull
request into main.

Step 2 waits for the checks of the pull request, merges it with --squash
--admin (the rules of main ask for a review that the author of the pull
request cannot give), then switches to main and pulls. xdbml.org deploys
from main by itself.
