xDBML 0.6.6 -- TablePartials as in DBML, records column order, release
Base: your local commit of xdbml-tablepartial-injection.zip (the TablePartial
delivery, on origin/main 59ac805). Built 2026-10-06.
This archive replaces the xdbml-0.6.6-release.zip of earlier today, which
left the settings and the indexes of a TablePartial out. It applies whether
that first archive was never unzipped, unzipped only, or committed.

WHAT IT DOES
------------
  1. 17.1: at the top level of an Entity or an Edge, a `~name` line brings
     what it brings in upstream DBML. Besides the fields: the keys and
     checks of the TablePartial, the entries of its `indexes` block, and
     its header color and its note where the entity declares none. Among
     partials the last one injected applies. Checked case by case against
     @dbml/core 10.2.0; the parser tests hold its values.
  2. The warning partial-indexes-not-carried of the first archive is gone.
  3. 26.1 (records): the implicit column order of a `records { }` block is
     the order of 17.1, each injected field at the place of its `~name`
     line. No tool reads that order today, so this is spec text only.
  4. The CHANGELOG section "Unreleased" becomes "v0.6.6", and the parser
     accepts `xdbml: 0.6.6`.

TWO POINTS WHERE I HAD TO PICK
------------------------------
  a. DBML has two table settings, headercolor and note, and both are
     carried. The settings xDBML adds (tags, synonyms, business_term,
     custom x_ properties) stay with the TablePartial: 17.1 says so.
  b. One difference from DBML remains, and is older than this work: when
     an entity and a TablePartial both declare a primary key, 10.4 gives
     the entity's key, where DBML makes one composite key of the two.

HOW TO APPLY AND RELEASE
------------------------
Unzip the archive at the root of the clone (C:\Repos\Hackolade\xdbml-spec),
then, from cmd.exe at the repo root:

    apply.cmd

apply.cmd copies nothing. It checks that 59ac805 is in the history of HEAD;
that each file of this delivery is, in HEAD, a version this delivery knows
(the TablePartial delivery, or the first 0.6.6 archive); that each unzipped
file holds this delivery's content; and that the working tree holds no
uncommitted change outside the delivery. It then runs the gate (npm run
check, mcp type-check) and prints these commands:

    git add <the files of the delivery>
    git commit -m "0.6.6: TablePartials as in DBML, records column order, release notes"
    tools\release-preflight.cmd 0.6.6
    tools\release.cmd 0.6.6

release-preflight.cmd changes nothing: it checks the npm login, that 0.6.6
is free for both packages, wrangler, the test suites and a clean tree.
release.cmd publishes @xdbml/parse then @xdbml/render at 0.6.6, deploys
the MCP server and the rendering API, commits the version bumps as
"release 0.6.6", pushes main with your local commits, and tags and
publishes the GitHub release from the v0.6.6 section of the CHANGELOG.
No push is needed before it, and no file is edited by hand.
