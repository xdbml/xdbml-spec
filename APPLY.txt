WHAT v0.4 ADDS
--------------
Relationships. Three subjects, one chapter.

  Foreign master (11.10 - 11.13)
    A `Ref` may carry a `foreign_master` flag recording where a duplicated
    attribute of denormalized data is mastered. Documentation only: it
    reaches no DDL, takes one attribute on each side, and a child attribute
    has at most one master. The four role markers fk / fm / dk / dm are
    computed from the declared relationships, and 11.13 fixes the line style
    for each relationship type.

  Roles, verbs, constraint type (11.14 - 11.15)
    `source_role` / `target_role` and `source_verb` / `target_verb` carry the
    wording that reads a relationship in each direction. `constraint_type`
    records identifying or non-identifying. All of it is authored, never
    derived, and never generated. 11.15.1 maps the constraint type onto the
    spellings used by Hackolade Studio, erwin, ER/Studio and PowerDesigner.

  Entity-level relationships (11.16)
    A `Ref` endpoint may name an entity rather than an attribute, so a
    relationship can be drawn between two concepts and refined in place
    without changing declaration kind. It states no cardinality, produces no
    attribute markers, and takes its reading direction from the operator
    alone.

Every v0.3 document remains valid. Documents using the new constructs
declare `xdbml: 0.4`.

RELEASING: PUBLISH AND DEPLOY
------------------------------
tools/PUBLISH-0.4.md in this package is the full runbook. The short version,
in order, because the steps depend on each other:

  1. Site      push to main; deploy.yml does the rest. Independent of npm --
               the site aliases the parser and renderer SOURCE, so it carries
               v0.4 as soon as it is pushed.

  2. parser    version 0.3.2 -> 0.4.0, then npm publish.
               New exports and diagnostics, no removals.

  3. renderer  version 0.3.1 -> 0.4.0 AND its @xdbml/parse range ^0.3.0 ->
               ^0.4.0, then npm publish. Must come after step 2: the range
               cannot resolve until the parser is on npm.
               Note the visible change -- the fk marker is now a two-letter
               pill, so a consumer with its own SVG snapshots will see diffs.

  4. mcp       ranges -> ^0.4.0, version 0.2.0 -> 0.3.0, SERVER_VERSION in
               src/index.ts to match, npm install, then npm run deploy
               (wrangler). Commit the refreshed lockfile: the Worker bundles
               from it, so an uncommitted lockfile means the deployed bundle
               does not match the repo.

  5. api       @xdbml/render range -> ^0.4.0, npm install, npm run deploy.

This package deliberately leaves every version and dependency range as it is
today, so the repo stays buildable and `npm ci` keeps working before any of
the above is done. Bumping a range to a version that is not yet on npm breaks
the install for everyone in between.

ONE THING TO KNOW ABOUT THE MCP SERVER
---------------------------------------
mcp/src/reference.ts is GENERATED from public/llms.txt and is what the
xdbml_reference tool returns. `npm run predeploy` regenerates it, so a hand
edit to the generated file is silently undone at deploy time. Edit
public/llms.txt and commit the regenerated file.

I hit this while updating the cheatsheet for v0.4: I edited both files and
they drifted, which `npm run check:reference` caught. Both now say the same
thing, and ci.yml runs that check so the drift cannot recur.

KNOWN GAPS, FOR AFTER THE DRAFT LANDS
--------------------------------------
1. Studio round trip. Whether Hackolade Studio persists a flag separating a
   default direction from an explicitly declared one is still unchecked. If
   it does, `-` alone will not round-trip and a setting is needed. Worth
   answering before the Studio plugin mapping, not after.

2. `from-mongodb` proposes foreign keys only. Duplicate values across
   collections are foreign master evidence, so `detectReferences()` could
   propose those too. An opportunity, not a defect.

3. Version gating covers only the v0.4 relationship constructs. Nothing read
   the declared version before this delta, so the module-system gates
   described in the grammar notes remain unimplemented. `versionAtLeast()`
   is written generally for them to adopt.

4. Identifying consistency is not checked. 11.15 offers it as something an
   implementation may do and report as a warning; the parser does not. The
   rule is written out in 11.15 if you want it later.

5. v0.4 has three more subjects planned: identifying relationships beyond the
   constraint-type property, associative entities for many-to-many, and
   supertype / subtype groups.
