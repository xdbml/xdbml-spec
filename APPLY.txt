xDBML -- Delta 4: the GitHub release is a command, and the caret fix
Base: origin/main at e5bc4f0 (v0.4 released).

WHY
---
The release runbook stopped at "push the tag", then described what to paste
into a web form. That left the last step manual, which is the thing you asked
me to stop doing. It also meant the release notes were retyped rather than
taken from the CHANGELOG, so the two can drift.

WHAT THIS ADDS
--------------
  tools\github-release.cmd 0.5
  tools\github-release.cmd 0.5 --prerelease

One command: generates the notes, refuses to tag a dirty tree or a HEAD that
differs from origin/main, creates and pushes the annotated tag with those
notes as its message, then creates the GitHub release through `gh`. Safe to
rerun -- an existing tag is left alone, an existing release has its notes
updated rather than duplicated.

Notes come from the `## v<version>` section of CHANGELOG.md via
scripts/release-notes.mjs, which also works standalone:

  node scripts\release-notes.mjs 0.4
  node scripts\release-notes.mjs 0.4 --out RELEASE-NOTES-v0.4.md

It strips the Status and Released lines (GitHub shows its own status) and
appends links to the versioned spec, the current draft, and the tagged
CHANGELOG. It exits non-zero when the version has no section, so a release
cannot be created with empty notes.

Without the GitHub CLI installed, the script still tags and pushes, writes
the notes file, and prints the exact URL and file to paste. Installing it
once removes that:

  winget install GitHub.cli
  gh auth login

ALSO: THE CARETS
----------------
cmd.exe treats `^` as its escape character, so every
`npm pkg set dependencies.@xdbml/parse=^0.4.0` you ran stored `0.4.0` with no
caret. main currently pins all four @xdbml dependency ranges exactly. It
resolves correctly, but a future 0.4.1 patch of the parser would not reach
the renderer, the MCP server or the API without a manual bump in each.

This package carries the corrected ranges:

  renderer  @xdbml/parse   ^0.4.0
  mcp       @xdbml/parse   ^0.4.0
            @xdbml/render  ^0.4.0
  api       @xdbml/render  ^0.4.0

Nothing else in those files changed -- the diff is four lines. No republish
is needed: the ranges affect future installs from source and the next
publish, not the packages already on npm. The published @xdbml/render@0.4.0
keeps its exact pin on parse 0.4.0, which is harmless and not worth a
republish to change.

In cmd.exe the caret must be doubled: `npm pkg set ...=^^0.4.0`. release.cmd
already does this, which is why it was not a problem there.

ALSO: tools/PUBLISH-0.4.md is deleted. RELEASE.md supersedes it, and two
runbooks drift.
